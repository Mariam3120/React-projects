## რას ვაშენებთ და რატომ

ჩვენ ვაშენებთ Bookmark Manager-ს: აპს, სადაც მომხმარებელი ინახავს საიტების ბმულებს, ამატებს, არედაქტირებს, შლის, ამაგრებს და აარქივებს.

ნამდვილი სერვერი არ გვაქვს, ამიტომ **ბექენდის იმიტაციად** ვიყენებთ `public/data/bookmarks.json`-ს. ეს ფაილი ჩვენი „მონაცემთა ბაზის" საწყისი მდგომარეობაა (seed data). მას `fetch()`-ით ვითხოვთ, ზუსტად ისე, როგორც ნამდვილ API-ს ვთხოვდით. `import`-ით **არ** შემოვიტანთ: ასე მონაცემი JavaScript-ის ნაწილი გახდებოდა და სერვერთან მუშაობის იმიტაცია დაიკარგებოდა.

პრობლემა ისაა, რომ ამ ფაილში ცვლილებას ვერ ჩავწერთ: ბრაუზერს სერვერზე ფაილის შეცვლა არ შეუძლია. ამიტომ იმისთვის, რომ მომხმარებლის ცვლილებები refresh-ის შემდეგ არ დაიკარგოს, ისინი ბრაუზერის **localStorage**-ში უნდა შევინახოთ.

ამისთვის სამი რამ გვჭირდება, და თითოეული წინაზეა დამოკიდებული:

1. **სახელები:** localStorage მონაცემს სახელით (key) ინახავს. გვჭირდება ფაილი, სადაც ეს სახელები ერთხელ ეწერება.
2. **ხელსაწყოები:** გვჭირდება ორი ფუნქცია, ერთი localStorage-იდან კითხულობს, მეორე მასში ინახავს.
3. **გადაწყვეტილებები:** გვჭირდება hook, რომელიც წყვეტს, **როდის** რა წაიკითხოს, როდის მოითხოვოს seed და როდის შეინახოს.

**მთავარი წესი:** აქ მზა კოდი არ არის. ყოველი ნაბიჯი ხსნის, რატომ გვჭირდება კონკრეტული ფაილი, და გაძლევს template-ს hint-ებით, ცარიელ ადგილებს კი შენ ავსებ. თუ პასუხს კოპირებით მიიღებ, ლოგიკას ვერ ისწავლი.

**წინაპირობები:** JavaScript-ის საფუძვლები (ფუნქციები, ობიექტები, მასივები), React-ის `useState` და `useEffect`, Vite-ზე შექმნილი პროექტი.

## ნაბიჯი 1: სახელები — `constants/storageKeys.js`

localStorage მონაცემს სახელით (key) ინახავს. DevTools → Application → Local Storage-ში ცხრილს ხედავ: მარცხნივ key, მარჯვნივ value. ჩვენ ორი ჩანაწერი დაგვჭირდება: ერთი bookmark-ებისთვის, მეორე theme-ისთვის.

ერთსა და იმავე key-ს რამდენიმე ადგილას დავწერთ: ჩაწერისასაც და წაკითხვისასაც. თუ ერთგან ტიპოს დავუშვებთ, აპი ერთ სახელზე შეინახავს, მეორიდან კი წაიკითხავს. შეცდომას არავინ გვაჩვენებს, მონაცემი უბრალოდ „გაქრება". ამიტომ იმისთვის, რომ key-ის სახელი ყველგან ზუსტად ერთნაირი იყოს, **გვჭირდება ფაილი, სადაც ეს სახელები ერთხელ ეწერება**, დანარჩენი კოდი კი მათ იქიდან იღებს.

კიდევ ერთი დეტალი: `localhost:5173`-ზე გაშვებულ **ყველა** პროექტს ერთი localStorage აქვს. თუ key-ს უბრალოდ `theme` დავარქმევთ, სხვა პროექტი მას გადაგვიწერს. ამიტომ სახელს წინ ვუმატებთ პროექტის სახელს, prefix-ს.

```js
// named export: სხვა ფაილები ამას { } ფრჩხილებით შემოიტანენ
// სახელი UPPER_SNAKE_CASE-ში — ასე აღინიშნება მნიშვნელობა, რომელიც არასდროს იცვლება
// Object.freeze — ობიექტს „ყინავს", კოდის ვერცერთი ნაწილი ვერ შეცვლის
export const ____________ = Object.freeze({
    // bookmark-ების key. ფორმატი: "პროექტის-სახელი:ჩანაწერის-სახელი"
    ________: "____________:________",

    // theme-ის key. prefix ზემოთ მოცემულის იდენტური
    ________: "____________:________",

```

**რა უნდა შეისწავლო:** named export და default export-ის სხვაობა; `UPPER_SNAKE_CASE` კონვენცია; `Object.freeze()` (MDN); localStorage-ის `setItem` / `getItem` და ის, რომ მხოლოდ string-ებს ინახავს.

**შემოწმება:** ეს ფაილი თავისით არაფერს აკეთებს, ის მხოლოდ სახელებს ინახავს. მუშაობაში ნაბიჯ 2-ში დაინახავ. აქ შეამოწმე, რომ export named-ია, ორივე მნიშვნელობას ერთი prefix აქვს და ფაილში `"use strict"` არ წერია (ES module-ები ისედაც strict mode-შია).

## ნაბიჯი 2: ხელსაწყოები — `utils/storage.js`

ახლა სახელები გვაქვს. იმისთვის, რომ მონაცემებზე მანიპულაცია შევძლოთ, **გვჭირდება, რომ შევქმნათ localStorage-დან წამკითხველი და შემნახველი ფუნქცია.**

`localStorage.getItem` / `setItem`-ს პირდაპირ რატომ არ ვიყენებთ? სამი მიზეზის გამო:

- localStorage **მხოლოდ string-ებს** ინახავს. მასივი შენახვამდე string-ად უნდა გადავაქციოთ (`JSON.stringify`), წაკითხვისას კი უკან (`JSON.parse`).
- `JSON.parse` **შეიძლება ჩავარდეს**: თუ storage-ში გაფუჭებული მონაცემია, შეცდომა მთელ აპს გააჩერებს და თეთრი ეკრანი დარჩება.
- `setItem`-იც შეიძლება ჩავარდეს, როცა storage სავსეა.

ამ ყველაფერს ერთხელ დავწერთ ორ ფუნქციაში, მერე კი მათ ორივე hook გამოიყენებს. ეს არის DRY.

ამ ფაილს `STORAGE_KEYS` **არ** სჭირდება: ფუნქციები key-ს პარამეტრად იღებენ, ამიტომ ნებისმიერ key-სთან იმუშავებენ.

### ოთხი ტესტი

ფუნქციები დროებით `App.jsx`-ში შემოიტანე და ტესტები **კომპონენტის გარეთ** დაწერე: კომპონენტის შიგნით ისინი ყოველ render-ზე გაეშვებოდა.

1. **ჩაწერა და წაკითხვა:** შეინახე მასივი, წაიკითხე fallback-ით `null` და დაბეჭდე `Array.isArray(...)`. უნდა ნახო მასივი და `true`. fallback `[]` არ გამოიყენო: მაშინ წარუმატებელი წაკითხვაც `true`-ს დაბეჭდავს და ტესტი ვერაფერს დაამტკიცებს.
2. **არარსებული key:** წაიკითხე ჩვეულებრივი string key, მაგალითად `"bookmark-manager:does-not-exist"`, fallback-ით `"MY FALLBACK"`, და შეადარე `===`-ით. უნდა დაბრუნდეს fallback.
3. **გაფუჭებული მონაცემი:** DevTools → Application → Local Storage-ში ხელით ჩაწერე `[{abc`, ჩამწერი ხაზი დააკომენტარე და refresh გააკეთე. უნდა დაბრუნდეს fallback, აპი კი არ უნდა ჩავარდეს.
4. **Key-ის სახელი:** იმავე პანელში ნახე, რომ key prefix-ით ინახება.

ტესტების შემდეგ დროებითი კოდი და ტესტის key-ები წაშალე.

## ნაბიჯი 3A: გადაწყვეტილებები — `hooks/useBookmarks.js`, ჩატვირთვა

ახლა გვაქვს სახელები და ფუნქციები, მაგრამ ვიღაცამ უნდა გადაწყვიტოს, **როდის** რა მოხდეს: აპის გახსნისას ჯერ localStorage შემოწმდეს; თუ იქ არაფერია (პირველი ვიზიტი), `fetch`-ით seed მოვითხოვოთ; სანამ მონაცემი მოდის, მომხმარებელმა loading დაინახოს; თუ რამე ჩავარდა, შეცდომა.

ეს ლოგიკა `App`-ში რომ დავწეროთ, კომპონენტი მონაცემების წამოღებით აივსებოდა. ამიტომ იმისთვის, რომ `App`-ს მხოლოდ მზა შედეგი მივაწოდოთ, **გვჭირდება custom hook**: ჩვეულებრივი ფუნქცია, რომლის სახელი `use`-ით იწყება და შიგნით React-ის hook-ებს იყენებს. `App` უბრალოდ დაიძახებს `useBookmarks()`-ს და მიიღებს `bookmarks`, `isLoading` და `error`.

### შემოწმება

`App.jsx`-ში hook **კომპონენტის შიგნით** გამოიძახე (hook-ები მხოლოდ კომპონენტში შეიძლება — Rules of Hooks). სამი მდგომარეობა (loading, error, წარმატება) ternary-ებით ერთმანეთში ნუ ჩასვამ: თითოეული ცალკე `if`-ით შეამოწმე და თავისი `return` დაუწერე (early return).

- ეკრანზე ჯერ loading ჩანს, შემდეგ bookmark-ების რაოდენობა.
- console-ში log ორჯერ იბეჭდება: ეს StrictMode-ია, არა bug.
- error-ის შესამოწმებლად `SEED_URL`-ში დროებით ტიპო ჩაწერე. Vite არარსებულ ფაილზე `index.html`-ს აბრუნებს სტატუსით 200, ამიტომ შეცდომა `response.json()`-ზე მოხდება (`Unexpected token '<'`). მთავარია, აპი არ ჩავარდეს და loading გაითიშოს.

## ნაბიჯი 3B: ავტომატური შენახვა

ახლა მონაცემი იტვირთება, მაგრამ ყოველ refresh-ზე ისევ seed მოდის: ჯერ არაფერს ვინახავთ. მომავალში bookmark-ების დამატება, რედაქტირება და წაშლა დაგვჭირდება, და თითოეულ ამ ფუნქციაში `saveToStorage`-ის ხელით გამოძახება გამეორება იქნებოდა. ამიტომ იმისთვის, რომ ყოველი ცვლილება თავისით შეინახოს, **გვჭირდება მეორე effect**, რომელიც bookmark-ების ყოველ ცვლილებაზე ეშვება.

ცალკე effect იმიტომ, რომ პირველი ერთხელ ეშვება (`[]`), ეს კი ყოველ ცვლილებაზე უნდა გაეშვას. ყოველ effect-ს ერთი დანიშნულება და ერთი dependency array აქვს.

### რატომ სჭირდება guard

თუ effect-ს პირობის გარეშე დავწერთ:

1. პირველ render-ზე `bookmarks` არის `[]`.
2. effect მაშინვე ეშვება და localStorage-ში `[]`-ს წერს.
3. ტაიმერის შემდეგ `loadBookmarks` storage-ში პოულობს `[]`-ს. ეს `null` არ არის, ამიტომ ფიქრობს, რომ მონაცემი უკვე არსებობს.
4. **seed აღარასდროს ჩაიტვირთება.**

მეორე ხაფანგი: თუ ჩატვირთვა ჩავარდა, `isLoading` ხდება `false`, `bookmarks` კი რჩება `[]`. guard-ის გარეშე ეს `[]` შეინახება და seed შემდეგ refresh-ზეც აღარ ჩაიტვირთება.

ცარიელი მასივი კი თავისთავად ლეგიტიმურია (მომხმარებელმა ყველაფერი წაშალა) და უნდა შეინახოს. ამიტომ guard **არ** ამოწმებს `bookmarks.length`-ს.

```js
// ფაილის თავში: import-ში დაამატე შემნახველი ფუნქციაც

// პირველი effect-ის ქვემოთ, return-ის ზემოთ:
useEffect(() => {
    // guard: ორი პირობა || ოპერატორით —
    // ჩატვირთვა ჯერ მიმდინარეობს? ან შეცდომა მოხდა?
    if (______ || ______) {
        return;
    }

    // შემნახველი ფუნქცია: bookmark-ების key და მიმდინარე მასივი
    // setBookmarks აქ არა! ეს effect state-ს მხოლოდ კითხულობს
    ______(STORAGE_KEYS.______, ______);
}, [______, ______, ______]); // სამივე state, რომელსაც effect იყენებს
```

**წესი, რომელიც უნდა დაიმახსოვრო:** effect-ში არასდროს შეცვალო ის state, რომელიც მისსავე dependency array-შია. ეს infinite loop-ს იწვევს. ESLint-ის `react-hooks/exhaustive-deps` წესი dependency array-ს შენთვის შეამოწმებს.

### ოთხი შემოწმება

1. **პირველი შენახვა:** Application → Local Storage-ში წაშალე key და refresh გააკეთე. key სრული მონაცემით უნდა შეიქმნას და არა `[]`-ით.
2. **Storage-იდან წაკითხვა:** Network tab-ში (Keep log / Preserve log **გამორთული**) refresh გააკეთე. `bookmarks.json` მოთხოვნა აღარ უნდა ჩანდეს.
3. **ხელით ცვლილება:** storage-ის value-დან წაშალე ერთი ჩანაწერი და refresh გააკეთე. რაოდენობა ერთით უნდა შემცირდეს.
4. **Error-ის შემთხვევა:** წაშალე key, `SEED_URL`-ში ჩაწერე ტიპო და refresh გააკეთე. error უნდა გამოჩნდეს, key კი არ უნდა შეიქმნას.

## გავრცელებული შეცდომები

ესენი რეალურად დაშვებული შეცდომებია ამ სამი ნაბიჯის წერისას. თუ რამე არ მუშაობს, ჯერ აქ მოძებნე.

| შეცდომა | რა ხდება | გამოსწორება |
| --- | --- | --- |
| `export Object.freeze({...})` | syntax error | named export-ს სახელი სჭირდება: `export const X = Object.freeze({...})` |
| `"use strict"` module-ის თავში | არაფერს ცვლის | ES module-ები ისედაც strict mode-შია, ხაზი ზედმეტია |
| `fetch(getFromStorage(...))` | seed არასდროს იტვირთება | `getFromStorage` თავად კითხულობს localStorage-ს, `fetch` აქ ზედმეტია |
| `response.json.parse()` | TypeError | სწორია `response.json()`; `JSON.stringify` საპირისპირო მიმართულებით მუშაობს |
| `return data` hook-ში | მონაცემი არსად მიდის | `setTimeout`-ს შედეგი არ აინტერესებს; გამოიყენე `setBookmarks(data)` |
| `throw new Error(setError(...))` | დამაბნეველი კოდი | `throw` მხოლოდ ტექსტს ქმნის, `setError` მხოლოდ `catch`-შია |
| `catch (error)`, როცა `error` state-იც არსებობს | shadowing | catch-ის პარამეტრს `err` დაარქვი |
| `styles.Tag`, CSS-ში კი `.tag` | class არ ეძლევა | JavaScript დიდ და პატარა ასოს არჩევს |
| `key={index}` | React-ის warning და bug-ები | გამოიყენე `id` ან სხვა სტაბილური მნიშვნელობა |
| cleanup-ში `setIsLoading(timeoutId)` | ტაიმერი არ უქმდება | cleanup-ში `clearTimeout(timeoutId)` |

- **Copilot:** სწავლის დროს inline suggestions გამორთე. ის კოდს წერს, მაგრამ არ ხსნის, და შედეგად ფაილში ისეთი ხაზები ჩნდება, რომელთა მნიშვნელობა არ იცი.
